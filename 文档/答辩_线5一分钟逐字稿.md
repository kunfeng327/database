# 答辩 · 线5 一分钟逐字稿

> 约 260 字，正常语速正好 1 分钟。**先理解，再脱稿用自己的话讲**，别死背。

---

我负责业务线五：补贴核算与质量监管。这条线要解决任务书里的两个痛点——补贴重复申报、监管缺留痕。

数据设计上，我建了补贴政策、补贴申报、质量抽查三张表，外加一张申报和订单的中间表。这里有个我主动做的改进：最初用逗号分隔字符串存订单号，我意识到它违反第一范式，就改成了中间表——这样申报金额才能真正追溯到每一笔订单，追溯查询也从全表扫描变成了纯索引关联。

业务上，补贴走"申报 → 街道审核 → 终审通过 → 拨付"，用"老人 + 政策 + 账期"的唯一约束防重复，用两个独立字段把审核和拨付状态分开，避免状态混用。监管这一侧，实现了"随机抽查 → 录评分 → 待整改 → 整改 → 恢复接单"的完整闭环，还在派单触发器里加了数据库层的兜底——有未完成整改的护工直接拒绝派单，抽查评分也会自动回写护工的评分。

最后我写了端到端的集成测试，覆盖了审核、拨付、抽查、整改和越权拦截这些场景。

## 被追问时的 3 个"救命点"（背下来）

1. **问"为什么拆中间表"** → "因为逗号分隔违反第一范式，没法建外键、也走不了索引；拆成中间表后满足第三范式，追溯查询从全表扫描变成主键等值关联。"

2. **问"怎么防重复申报"** → "数据库层用 `UNIQUE(老人, 政策, 账期)` 兜底，应用层申报前再校验一次。"

3. **问"并发下两人同时审核同一单怎么办"** → "DAO 里用 `SELECT ... FOR UPDATE` 行锁，同一时刻只有一个事务能改状态。"
