## 2. 数据完整性机制

### 2.1 表级约束

数据库通过主键、外键、唯一键、枚举域和检查约束落实实体、参照及业务数据完整性。

| 约束场景 | 数据库实现 |
|---|---|
| 老人归属社区 | `elder.community_id` 外键引用 `community.community_id`；身份证号唯一，并通过 CHECK 校验长度为 18。 |
| 能力评估 | `assessment.elder_id` 外键引用老人；评分限制在 0–100；有效期必须晚于评估日期。 |
| 生效照护计划 | 生成列 `active_elder_id` 配合唯一键，限制同一老人同时只有一个生效计划。 |
| 排班 | 护理员、日期、班次组成唯一约束；`booked` 必须在 0 与 `capacity` 之间。 |
| 派单与工时 | 派单引用订单和护理员；工时的 `dispatch_id` 唯一且引用派单；签退时间不得早于签到时间。 |
| 补贴申报 | 同一老人、政策和账期设置联合唯一键，阻止重复申报。 |
| 质量抽查 | 至少关联订单或护理员；评分限定在 0–100；抽查状态、评分与整改状态之间设置 CHECK 约束。 |
| 账号角色 | `sys_user.role` 使用枚举；家属账号必须绑定老人，护工账号必须绑定护理员。 |

### 2.2 事务与错误回滚

`app.py` 中的 `run_in_transaction(fn)` 在一个数据库事务中执行写操作：成功后提交，发生异常时回滚并关闭连接。触发器使用 `SIGNAL SQLSTATE '45000'` 拒绝不符合规则的写入；事务封装将数据库错误映射为业务错误响应。

## 4. 存储过程

| 存储过程 | 功能 |
|---|---|
| `sp_pause_expired_plans()` | 按每位老人评估记录中的最大 `expire_date` 判断有效期；过期后将其生效照护计划改为“暂停”，并返回暂停数量。 |
| `sp_batch_create_schedule(...)` | 按护理员、起止日期、班次和容量批量创建排班；遇到同日班次冲突时跳过，并通过输出参数返回创建数量。 |

## 5. 触发器

| 触发器 | 事件 | 完整性/保护规则 |
|---|---|---|
| `tr_care_plan_before_insert` | 插入照护计划前 | 生效计划必须对应有效能力评估。 |
| `tr_care_plan_before_update` | 更新照护计划前 | 计划转为生效时再次校验能力评估有效期。 |
| `tr_dispatch_before_insert` | 插入派单前 | 校验订单状态、护理员在岗状态、证书有效期、未完成质检整改及排班余量。 |
| `tr_dispatch_check_item` | 插入派单前 | 校验护理员已获准承接订单对应服务项目。 |
| `tr_dispatch_after_insert` | 插入派单后 | 将匹配排班的已接单量加一。 |
| `tr_dispatch_after_confirm` | 更新派单后 | 家属确认服务完成时，将订单状态回写为“已完成”。 |
| `tr_vital_sign_before_insert` | 插入体征前 | 按指标类型和阈值自动设置体征标记。 |
| `tr_emergency_before_update` | 更新应急事件前 | 对待响应且超过等级时限的事件升级；补录响应人或处置结果时推进事件状态。 |
| `tr_work_hour_before_update` | 更新工时前 | 签退时校验时间；围栏通过则计算有效工时，围栏异常则置零并转人工复核。 |
| `tr_work_hour_after_update` | 更新工时后 | 有效工时通过认定后累加到护理员累计工时。 |
| `tr_schedule_before_insert` | 插入排班前 | 阻止同一护理员同日重复班次及“全天”与半天班次冲突。 |

应急升级触发器定义为 `BEFORE UPDATE ON emergency`：升级逻辑在应急记录更新时执行，不是独立的定时任务。

## 6. 安全策略

### 6.1 身份认证与账号保护

- 登录通过 `sys_user.username` 查询账号，并校验账号状态和密码摘要。
- 当前密码摘要为 `SHA256(salt + password)`，盐值存放在 `sys_user.salt`。
- 连续输错 5 次后锁定账号 10 分钟；登录成功后清零失败次数并更新最后登录时间。
- 会话有效期为 30 分钟，并设置 `HttpOnly` Cookie。
- `APP_SECRET_KEY` 用于 Flask 会话签名。部署时从环境变量注入专用密钥，不使用源码中的演示默认值。
- 生产环境采用 Argon2id、bcrypt 或 scrypt 等密码专用哈希算法保存密码摘要，并启用 HTTPS、`Secure` Cookie 和适用的 `SameSite` 策略。

### 6.2 角色授权与数据范围

系统在 API 层执行角色访问控制，角色包括家属、护工、社区管理员、机构负责人和监管人员。`login_required(roles=...)` 校验登录身份和接口允许角色；业务查询按家属绑定老人、护工绑定护理员等关系限制数据范围。

订单派单、改派和护理员推荐接口只允许社区管理员访问；服务完成接口允许护工或社区管理员访问。当前实现属于应用层 RBAC，数据库表中的角色枚举不等于 MySQL 原生数据库账号权限。

### 6.3 SQL 与业务数据保护

- 数据访问使用参数化 SQL，业务写操作置于事务中，失败时回滚。
- 触发器拒绝不符合派单、资质、排班容量、工时和质检规则的写入。
- 老人视图将身份证号以掩码形式返回；健康体征、联系方式和身份证号只向有业务权限的接口开放。
- 数据库账号按运行职责配置最小权限；生产环境分离应用账号和备份账号，不使用数据库管理员账号运行应用。
- 日志不记录明文密码、完整身份证号或不必要的健康信息；业务错误响应不泄露 SQL、连接串或服务器内部细节。

### 6.4 备份与恢复

使用 `mysqldump` 导出数据库结构和数据，备份文件限制访问并加密保存；通过隔离恢复库验证备份可用性。生产环境启用 binlog 并保留恢复所需日志，以支持时间点恢复。恢复后检查表结构、关键业务记录、视图、存储过程和触发器。

### 6.5 个人信息与健康数据

老人姓名、身份证号、监护人联系方式及体征记录属于敏感业务数据。系统按业务角色控制读取范围，列表视图对身份证号脱敏；数据导出、备份和日志遵循最小必要原则。生产环境对存储介质和备份文件启用加密，并通过 HTTPS 传输数据。
