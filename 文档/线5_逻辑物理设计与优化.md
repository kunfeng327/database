# 线5 补贴核算与质量监管：逻辑设计、物理设计与优化

> 本文档补充线5 的**逻辑结构设计、物理结构设计（索引方案）、执行计划与优化、非功能性需求、风险控制**，与《线5_补贴与质量监管_设计说明.md》配套，形成"需求分析→概念→逻辑→物理→实施→优化"的完整证据链。

## 1. 非功能性需求

| 类别 | 需求 | 落实手段 |
|---|---|---|
| 一致性 | 审核/拨付状态流转严格、防重复申报 | 状态机 DAO + `FOR UPDATE` 行锁 + `UNIQUE(elder_id,policy_id,claim_period)` |
| 可追溯 | 申报金额可回溯到订单与工时 | 中间表 `subsidy_claim_order` + 追溯视图 `v_claim_trace_detail` |
| 性能 | 申报追溯、区县统计高频查询快速响应 | 中间表主键/外键索引（见 §3） |
| 安全 | 分级审核、越权拦截 | RBAC：监管人员审核、护工只能提交本人整改 |
| 可审计 | 审核人、审核时间、拨付时间、整改全程留痕 | `reviewer/audited_at/paid_at/inspector/rectified_at` 字段 |

## 2. 逻辑结构设计

### 2.1 关系模式（主键下划线、外键标注）

```
补贴政策(政策编号, 适用区县, 对象类别, 补贴项目, 补贴标准, 结算周期, 生效日期, 失效日期)
  主键：政策编号    外键：补贴项目 → 服务项目.项目编号

补贴申报(申报编号, 档案编号, 政策编号, 申报周期, 申报金额, 审核状态, 拨付状态, 审核人, 审核时间, 拨付时间, 创建时间)
  主键：申报编号
  外键：档案编号 → 老人档案；政策编号 → 补贴政策
  唯一：(档案编号, 政策编号, 申报周期)      -- 同一老人同期同项目不得重复申报

补贴申报订单关联(申报编号, 订单编号)
  主键：(申报编号, 订单编号)                 -- 复合主键（多对多中间表）
  外键：申报编号 → 补贴申报；订单编号 → 服务订单

质量抽查(抽查编号, 订单编号, 护工编号, 抽查方式, 评分, 问题标签, 整改要求, 整改结果,
         抽查状态, 整改状态, 抽查人, 抽查时间, 整改完成时间)
  主键：抽查编号
  外键：订单编号 → 服务订单；护工编号 → 护工档案
  约束：订单编号 与 护工编号 至少其一非空
```

### 2.2 函数依赖

```
补贴政策：    政策编号 → 适用区县, 对象类别, 补贴项目, 补贴标准, 结算周期, 生效日期, 失效日期
补贴申报：    申报编号 → 档案编号, 政策编号, 申报周期, 申报金额, 审核状态, 拨付状态, ...
            (档案编号, 政策编号, 申报周期) → 申报编号    -- 候选键，保证防重复
补贴申报订单关联：(申报编号, 订单编号) → ∅               -- 仅含两个外键，无其他非主属性
质量抽查：    抽查编号 → 订单编号, 护工编号, 抽查方式, 评分, ..., 整改状态, ...
```

### 2.3 第三范式验证（重点：中间表改造）

| 范式 | 要求 | 本线处理 |
|---|---|---|
| 1NF | 字段原子、不可再分 | **改造前** `subsidy_claim.order_ids` 用逗号分隔存多个订单号（如 `'1,2,3'`），违反 1NF；**改造后**拆出 `subsidy_claim_order(申报编号, 订单编号)` 中间表，每个字段单一值 |
| 2NF | 消除部分依赖 | 中间表主键为 `(申报编号, 订单编号)` 复合键，且**只含这两个外键属性、无其他非主属性**，不存在只依赖主键一部分的情况 |
| 3NF | 消除传递依赖 | `适用区县/对象类别/补贴标准` 归属补贴政策表、订单金额/工时归属订单与工时表、老人姓名归属老人表，本线四表均只存外键编号，无"非主键字段依赖另一个非主键字段" |

> **答辩要点**：原 `order_ids + FIND_IN_SET` 实现虽然能"追"，但既违反 1NF，又无法建外键约束、无法走索引（全表扫）。改中间表后同时满足"第三范式"和"申报可追溯"两条任务书要求。

## 3. 物理结构设计（索引方案）

| 表 | 索引名 | 字段 | 类型 | 理由 |
|---|---|---|---|---|
| subsidy_policy | PRIMARY | policy_id | 主键 | 唯一标识 |
| subsidy_policy | idx_policy_item | item_id | 普通 | 外键，关联查询"某项目的补贴政策" |
| subsidy_claim | PRIMARY | claim_id | 主键 | 唯一标识 |
| subsidy_claim | uk_claim_no_dup | (elder_id, policy_id, claim_period) | 唯一 | **防重复申报**（核心约束） |
| subsidy_claim | idx_claim_audit_pay | (audit_status, pay_status) | 普通 | 按"待审核/未拨付"筛选审核队列 |
| subsidy_claim | idx_claim_period | claim_period | 普通 | 按账期统计 |
| subsidy_claim_order | PRIMARY | (claim_id, order_id) | 主键 | 复合主键，申报→订单追溯 |
| subsidy_claim_order | idx_sco_order | order_id | 普通 | 从订单反查所属申报 |
| quality_inspection | PRIMARY | inspection_id | 主键 | 唯一标识 |
| quality_inspection | idx_quality_caregiver_status | (caregiver_id, rectification_status) | 复合 | **"某护工是否有待整改"高频校验**（派单触发器 + 质量画像查询都用它） |
| quality_inspection | idx_quality_order | order_id | 普通 | 按订单查抽查 |
| quality_inspection | idx_quality_inspected | inspected_at | 普通 | 按抽查时间排序 |

## 4. 执行计划与优化（实测 EXPLAIN）

### 4.1 申报追溯查询（改造前后对比）

查询：`subsidy_claim → subsidy_claim_order → service_order → service_item → dispatch → work_hour`

**改造后实测 EXPLAIN**（MySQL 8.0）：

| 表 | 访问类型 type | 使用的键 key |
|---|---|---|
| subsidy_claim cl | index | PRIMARY（反向扫描） |
| elder e | eq_ref | PRIMARY |
| subsidy_claim_order sco | ref | PRIMARY（claim_id） |
| service_order o | eq_ref | PRIMARY（order_id） |
| service_item si | eq_ref | PRIMARY |
| dispatch d | ref | idx_disp_order |
| work_hour wh | eq_ref | dispatch_id（唯一） |

**结论**：7 张表全部 `eq_ref/ref` 等值关联，**零全表扫描**。

**对比改造前**：原 `JOIN service_order o ON FIND_IN_SET(o.order_id, cl.order_ids) > 0` 会退化为 `type=ALL`（对 service_order 全表扫 + 逐行 FIND_IN_SET 判断），且 `order_ids` 无外键约束。改造后既满足 3NF，又把追溯从"全表扫"变成"主键等值关联"。

### 4.2 护工质量画像查询

`caregiver LEFT JOIN quality_inspection ON caregiver_id ... GROUP BY`

| 表 | 访问类型 | 使用的键 |
|---|---|---|
| caregiver cg | ALL（31 行小表，可接受） | — |
| quality_inspection qi | ref | idx_quality_caregiver_status（复合索引左前缀 caregiver_id） |

**结论**：质量抽查表命中复合索引；护工表 31 行全扫可忽略（小表），`Using temporary` 为 GROUP BY 正常开销。

### 4.3 优化结论

- 中间表改造使追溯查询从全表扫描优化为纯索引等值关联，是本次最关键的 SQL 优化；
- 防重复申报唯一索引同时服务"业务约束"和"查询加速"双重目的；
- `idx_quality_caregiver_status` 复合索引同时服务派单触发器的整改校验与质量画像聚合。

## 5. 风险与安全控制

| 风险 | 控制手段 |
|---|---|
| 重复申报（恶意/误操作） | 数据库层 `UNIQUE(elder_id, policy_id, claim_period)` 兜底 |
| 拨付状态与审核状态错乱 | 两个独立枚举字段分离，DAO 状态机校验 + `FOR UPDATE` 行锁防并发 |
| 申报金额虚高/无法追溯 | 申报时校验每笔订单须有"自动认定/复核通过且 >0"的有效工时，缺一拒绝 |
| 抽查流于形式 | 按比例随机抽样（至少 1 条）、评分低于 80 或有标签自动进入待整改 |
| 问题护工继续接单 | 派单触发器 `tr_dispatch_before_insert` 拦截"待整改/整改中"护工 |
| 越权（监管代填整改、护工改他人整改） | RBAC 接口级校验 + DAO 内校验"整改任务归属当前护工" |
